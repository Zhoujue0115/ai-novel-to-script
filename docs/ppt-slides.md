┌──────────────────────────────────────────┐

**讲：** 小说改编剧本有四个痛点——人工整理费时间、作者缺乏剧本格式经验、直接问 ChatGPT 输出不规范、自由文本不方便后续编辑。我们的方案是：把小说转成结构化 YAML，每条对白、每个场景都有明确字段，可校验、可编辑、可以追溯原文。

## 第 4 页 — 技术架构

```
┌──────────────────────────────────────────┐
│              系统架构                     │
│                                          │
│  前端 (React + Vite)                     │
│  ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐   │
│  │ Cover│→│Input │→│YAML  │→│Preview│   │
│  └──────┘ └──┬───┘ └──────┘ └──────┘   │
│              │                           │
│  ─ ─ ─ ─ ─ ─│─ ─ Vite Proxy ─ ─ ─ ─ ─│
│              ▼                           │
│  后端 (FastAPI)                          │
│  ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐   │
│  │Pydantic│→│Prompt│→│DeepSeek│→│YAML │   │
│  │ 校验   │ │Builder│ │ API  │ │校验  │   │
│  └──────┘ └──────┘ └──────┘ └──────┘   │
│                                          │
│  生成策略（按章节数自适应）               │
│  ≤6章: LangChain 三步链                  │
│  7-20章: 基础 Prompt                     │
│  >20章: 滑动窗口批量 + RAG 检索          │
└──────────────────────────────────────────┘
```

**讲：** 前端是 React + Vite 单页应用，后端 FastAPI。请求进来先过 Pydantic 校验，然后根据章节数自动选生成策略——6 章以内用 LangChain 三步链（先分析角色场景、再生成剧本、最后自检修正），7 到 20 章基础生成，20 章以上滑动窗口批量加 RAG 检索增强。生成结果过 YAML 校验后返回前端展示。

## 第 5 页 — 技术亮点

```
┌──────────────────────────────────────────┐
│              技术亮点                     │
│                                          │
│  🔗 LangChain 三步链                      │
│     分析角色与场景 → 生成 YAML → 自检修正  │
│     比单次 Prompt 质量提升明显             │
│                                          │
│  🔍 RAG 全文检索                          │
│     ChromaDB 索引全文，检索片段注入生成     │
│     sentence-transformers 中文向量化       │
│                                          │
│  📡 SSE 流式推送                          │
│     生成过程实时推送进度，不再干等          │
│                                          │
│  🔧 零额外依赖调大模型                     │
│     Python 标准库 urllib 直连 DeepSeek     │
│     API 失败自动重试 3 次                  │
│                                          │
│  📊 剧本统计分析                          │
│     场景数/对白占比/角色台词排行           │
└──────────────────────────────────────────┘
```

**讲：** 五个技术亮点。LangChain 三步链把一次 prompt 拆成分析→生成→自检，每一步专注一件事，输出质量更高。RAG 用 ChromaDB 做全文索引，生成长文时自动检索相关片段注入 prompt。SSE 让前端实时看到生成进度。我们直接用 Python 标准库调 DeepSeek API，没有引入任何第三方 SDK，而且加了失败重试。生成后自动统计场景数、对白占比、角色台词排行。

## 第 6 页 — YAML Schema 设计

```
┌──────────────────────────────────────────┐
│           YAML Schema 设计                │
│                                          │
│  7 层嵌套结构：                           │
│  title → metadata → source_chapters      │
│       → characters → settings            │
│       → scenes → beats → adaptation_notes│
│                                          │
│  beats 的 5 种类型：                      │
│  🟢 对白 dialogue    — 带 character 字段  │
│  🔵 动作 action      — 带 character 字段  │
│  🟣 旁白 narration   — 环境/心理描写      │
│  🟠 独白 inner_monologue — 内心活动       │
│  ⚪ 提示 stage_direction — 镜头/舞台指示  │
│                                          │
│  设计原则：以场景为核心 / 保留章节来源     │
│           统一角色管理 / 便于编辑扩展      │
└──────────────────────────────────────────┘
```

**讲：** YAML Schema 是整个项目的核心。7 层嵌套结构，从标题到改编说明，每一层都有明确含义。beats 是最小粒度，分 5 种类型——对白、动作、旁白、内心独白、舞台提示。设计原则是以场景为核心而不是以章节为核心，保留来源章节引用方便追溯，统一角色管理避免名字不一致。
